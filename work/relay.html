Case study — Relay

Relay
messaging infrastructure

The gateway started at 200 connections and worked beautifully. Real customers arrived, and by 2,000 connections the p99 delivery curve went vertical. Relay carries 40,000 now — and no client integration had to change.

01 — The brief A demo-scale gateway, and fourteen live integrations we were not allowed to break.

The original gateway was a single event loop behind a global lock, and at the scale it was designed for that was the right call — simple, correct, and fast enough. It stayed correct well past the scale it was designed for, which is how these things usually go.

Around 2,000 concurrent connections the p99 delivery time stopped being a number and became a cliff. One slow consumer could hold the lock long enough to stall every other connection on the box, and the failure looked like network trouble from the outside.

The constraint shaped every decision after it: the client SDK's public API was already shipped, and fourteen customer integrations were live against it. We could not ask anyone to upgrade, and we could not ship a flag day. Whatever we built had to make the old path keep working.

02 — What I built Shards that own their own fate, a negotiable protocol, and deploys that drop nothing.

Relay is a sharded gateway in front of a thin routing layer. Nothing global survives: each shard has its own event loop, its own connection table and its own backpressure, so no consumer can stall the fleet.

  • Sharded gateway — connections partitioned across independent shards; a slow consumer only ever penalises its own shard.
  • Versioned wire protocol — handshake negotiates a version, so old frames keep parsing exactly as before while new frames add batching and resume tokens.
  • Sticky session routing — a reconnect lands on the shard that already holds that session's state, instead of starting cold.
  • Adaptive heartbeat + idle eviction — keeps the connection table honest behind load balancers that hold dead sockets open.
  • Graceful drain — a shard hands its connections off during a deploy with no dropped frames, which is what makes rolling restarts possible at all.
03 — The hard part Backpressure, protocol evolution without a flag day, and measuring the right number.

Backpressure before memory

Each connection gets a bounded send queue. When one is full the shard stops pulling for that consumer and applies a documented drop policy rather than growing until the box dies. Dropped messages carry resume tokens, so a slow client resumes and refetches instead of silently losing events — recoverable is a much better failure mode than lost.

Evolving the protocol without a flag day

Everything new is opt-in at the handshake: existing clients take the old path untouched, upgraded clients negotiate batching. The cost of "zero breaking changes" is that you have to keep the old path working — so it was written as a first-class, tested path, not a compatibility shim, and retired by usage data rather than by a deadline.

The number worth measuring

Throughput was the wrong metric: a gateway can push millions of messages a second while feeling broken. We measured p99 delivery time instead, because that is what a customer's UI actually shows. It also turned out to be the metric that caught the file-descriptor ceiling before users did.

04 — Outcome Two hundred to forty thousand, with no integration noticing.

Breaking changes

Relay carries 40,000 concurrent connections at 11ms p99 delivery, on hardware that would not have survived the original design. The sharding split was a two-week change; the drain protocol and the send-queue caps were what made it safe to ship.

The result that mattered commercially: zero breaking changes. All fourteen original integrations are still live, none of them ever had to upgrade, and the ones that have upgraded did it for the batching rather than because we made them.
